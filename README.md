# Multi-Agent System Architectures Benchmark in Software Development

Supporting experimental data for the undergraduate thesis **Multi-Agent System Architectures Benchmark in Software Development** by **Tran Le Thai Son**, Faculty of Information Technology, **Ton Duc Thang University**, 2026. Thesis advisor: **Dr. Tran Thanh Phuoc**.

This repository contains the thesis report, saved benchmark runs, generated patches, agent telemetry, evaluation logs, and aggregate results. It supports inspection of the experiments and recomputation of the published summaries. The agent implementations and benchmark execution CLI described in the thesis are not included in this data snapshot.

## Research context

The study investigates how communication topology affects automated software repair. It compares two multi-agent systems with the same specialist roles: Project Manager, Engineer, Code Reviewer, and Quality Assurance (QA).

- **Centralized MAS** (`mas_centralize`): a hub-and-spoke architecture in which the Project Manager coordinates specialist work and routes transitions.
- **Decentralized MAS** (`mas_decentralized`): a peer-to-peer architecture in which agents can hand off work directly according to the current task state.

## Experimental scope

The main comparison uses **50 instances from the SWE-bench Lite test split**, selected through a repository-balanced round-robin strategy. Each instance was executed **once per architecture**, producing **100 saved runs** with a task timeout of **1,800 seconds**.

The selected tasks cover 12 repositories: Astropy, Django, Flask, Matplotlib, Pylint, pytest, Requests, scikit-learn, seaborn, Sphinx, SymPy, and xarray. Task metadata records the repository, base commit, issue description, and benchmark test criteria.

Functional correctness is determined by SWE-bench grading: the repair must satisfy the fail-to-pass tests while preserving the pass-to-pass regression tests. Agent completion messages and internal QA verdicts are separate from this external evaluation.

## Repository layout

```text
.
├── README.md
├── baocao.pdf                       # Full thesis report
├── reports/
│   └── benchmark/
│       ├── report.md                # Aggregate results and timing explanation
│       ├── summary.csv              # Summary table for analysis
│       ├── summary.json             # Summary metrics and provenance fields
│       └── paired_deltas.json       # Task-level differences between architectures
└── runs/
    └── benchmark/
        ├── grade_runs.log           # Grading pipeline log
        ├── mas_centralize/
        │   └── <instance_id>/repeat_1/
        └── mas_decentralized/
            └── <instance_id>/repeat_1/
```

Each run directory contains artifacts such as:

| Artifact | Purpose |
| --- | --- |
| `run_record.json` | Instance and arm identifiers, execution status, duration, telemetry summary, and external grading outcome |
| `task_metadata.json`, `task_context.json` | Benchmark task, repository context, and evaluation criteria |
| `prompt.txt` | Task prompt supplied to the system |
| `patch.diff` | Repair patch generated by the agents |
| `test_patch.diff` | Benchmark test patch |
| `result.json` | Workflow completion information and internal validation verdicts |
| `telemetry.json` | Token usage, messages, handoffs, tool events, and available timing provenance |
| `predictions.jsonl` | Prediction input for the grading harness |
| `<arm>.benchmark.json` | SWE-bench grading summary |
| `stdout.log`, `stderr.log` | Agent execution output |
| `grade.stdout.log`, `grade.stderr.log`, `logs/` | Grading output, test results, and image-build logs |
| `project_board/`, `knowledge_base/`, `workspace/` | Available collaboration artifacts and workspace contents |

Artifact availability can vary by run. Absolute paths embedded in JSON files refer to the original execution environment; locate files through the relative directory structure above.

## Interpretation and reuse

The data supports the thesis's analysis of correctness, token consumption, communication patterns, patch scope, and failure cases. Token counts measure recorded model usage; monetary cost requires model-specific pricing and usage details.

The main limitations are the 50-task sample, one execution per architecture per task, incomplete baseline coverage, evaluation-environment issues. The proposed hybrid coordination model in the thesis is a direction for future work; this snapshot contains the two evaluated MAS architectures.

When referencing this dataset, acknowledge the thesis author and identify the architecture, instance set, metric source, and evaluation scope used. A bibliographic reference for the accompanying thesis is:
